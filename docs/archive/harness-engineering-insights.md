# Learn Harness Engineering 深度洞察报告

> 来源：https://walkinglabs.github.io/learn-harness-engineering/zh/
> 一门专注于 AI 编程智能体工程化落地的课程，深度研究 OpenAI 与 Anthropic 在 Harness Engineering 领域的前沿理论与实践

---

## 一、核心定义

### 1.1 什么是 Harness

**Harness = 模型权重之外的一切工程基础设施。**

课程给出了精确的五子系统定义：

| 子系统 | 职责 | 关键产出 |
|--------|------|---------|
| **指令（Instructions）** | 告诉 agent 项目是什么、怎么跑、什么不能做 | `AGENTS.md`、`CLAUDE.md`、专题文档 |
| **工具（Tools）** | agent 可用的操作能力 | Shell 访问、包管理器、git、lint |
| **环境（Environment）** | 自描述、可重现的执行环境 | `pyproject.toml`、`.nvmrc`、Docker |
| **状态（State）** | 跨会话持久化的进度和决策记录 | `PROGRESS.md`、`DECISIONS.md`、git commits |
| **反馈（Feedback）** | 可执行的验证命令和错误修复指导 | `make test`、`make check`、端到端测试 |

**核心类比：** "同一匹马（模型），配上不同的马具（harness），表现天差地别。"

### 1.2 关键实验证据

**Anthropic 对照实验（2025-2026）：**
- 同一模型 Opus 4.5，同一 prompt："做一个 2D 复古游戏编辑器"
- 裸跑：20 分钟，$9，游戏核心功能跑不起来
- 配上完整 harness（planner + generator + evaluator 三 agent 架构）：6 小时，$200，游戏可以正常游玩
- **模型没变，变的只是 harness**

**OpenAI 100 万行代码实验（2025）：**
- 3 个工程师，5 个月，不写代码只让 Codex 写
- 1,500 个 PR，人均每天 3.5 个
- 核心发现：问题几乎从来不是"模型不够努力"，而是"它还缺什么"

## 二、五层防御模型

课程将 agent 失败归因到五层防御结构，这是整个 harness 工程的诊断框架：

```
Layer 1: 任务规范 — 需求是否被清晰、完整地表达？
Layer 2: 上下文供给 — agent 需要的信息是否在它能找到的地方？
Layer 3: 执行环境 — 环境是否自描述、可重现？
Layer 4: 验证反馈 — agent 有没有办法知道自己做得对不对？
Layer 5: 状态管理 — 跨会话的知识和进度是否被持久化？
```

**诊断原则：** 遇到失败先归因到具体层，不要笼统地说"模型不行"。每次失败都是 harness 暴露了一个结构性缺陷的信号。

## 三、十二讲核心洞察

### L01 — 模型能力强 ≠ 执行可靠

**关键数据：** SWE-bench Verified 上最强 agent 通过率约 50-60%，但这个数字只适用于有明确 issue 描述和现成测试的任务。真实需求模糊、隐含业务规则散落各处时，通过率远低于此。

**五种典型失败模式：**
1. 需求描述模糊 → agent 只能猜
2. 隐性约定没写下来 → agent 无从遵守
3. 环境配置有缺口 → agent 把宝贵上下文花在修环境上
4. 缺少验证手段 → agent 自己觉得做完了就算完成
5. 跨会话状态丢失 → 每个新会话都要重新探索

**"上下文焦虑"（Context Anxiety）：** 当 agent 感觉上下文快满了，它们会匆忙结束当前工作，跳过验证步骤，选简单的方案而不是最优方案。

**核心原则：** 遇到失败，先修 harness，后换模型。换模型是成本最高的选择。

### L02 — Harness 到底是什么

**五子系统评判标准：**
- 指令子系统：agent 能不能只读仓库就回答"这是什么项目"、"怎么跑"、"怎么验证"
- 工具子系统：最小权限原则，不要因安全顾虑禁用 shell
- 环境子系统：环境状态自描述，用 `pyproject.toml`/`package.json` 锁定依赖
- 状态子系统：长任务必须有 `PROGRESS.md` 记录完成/进行中/阻塞
- 反馈子系统：投入产出比最高的子系统，先写清楚验证命令

**控制变量排除法：** 逐个移除五个子系统，看哪个缺失时性能下降最多。下降最多的组件边际贡献最大。但定位真正瓶颈要靠失败记录和归因，不能只靠拆除实验。

**四个阶段对照实验：**
- 阶段 1（只有 README）：成功率 20%
- 阶段 2（+ AGENTS.md）：成功率 60%
- 阶段 3（+ 验证命令）：成功率 80%
- 阶段 4（+ 进度文件）：成功率 80-100%
- **四次迭代，模型一个字没改**

### L03 — 让代码仓库成为唯一的事实来源

**核心原则：** 不在仓库里的知识对 agent 来说等于不存在。

**"全新会话测试"（衡量仓库质量的金标准）：** 开一个全新 agent 会话，不给任何口头上下文，只让它看仓库内容，看它能不能回答五个问题：
1. 这是什么系统？
2. 怎么组织的？
3. 怎么运行？
4. 怎么验证？
5. 现在进度如何？

**知识地图四原则：**
1. 知识靠近代码（模块级 `ARCHITECTURE.md` 优于全局单一文档）
2. 标准化入口文件（`AGENTS.md` 50-100 行，让 agent 快速回答三个基本问题）
3. 最小但完备（每条知识有明确使用场景，但五问题都必须有答案）
4. 和代码一起更新（文档跟代码变更绑定，CI 提醒检查文档是否需要更新）

**ACID 原则应用于 Agent 状态管理：**
- 原子性（Atomicity）：每次逻辑操作用一个 git commit 原子化
- 一致性（Consistency）：定义"一致状态"的验证谓词，不一致不 commit
- 隔离性（Isolation）：多 agent 并发用独立进度文件或 git 分支隔离
- 持久性（Durability）：跨会话必须的知识必须写到 git 跟踪的文件里

**"发现成本"概念：** agent 在仓库里找到一条关键信息需要消耗多少上下文。信息放得越隐蔽，发现成本越高，留给实际任务的预算越少。

### L04 — 把指令拆分到不同文件里

**"巨型指令文件"陷阱：** 每次出问题就"加条规则"，文件从 50 行膨胀到 600 行，但表现反而变差。

**三个破坏性后果：**
1. **上下文预算被吃掉：** 600 行的 `AGENTS.md` 占用 10,000-20,000 tokens，在 128K 窗口中占 8-15%
2. **中间迷失（Lost in the Middle）：** Liu et al., 2023 — LLM 对长文本中间部分的信息利用效率显著低于两端。埋在第 300 行的关键约束被忽略概率非常高
3. **优先级冲突：** 硬约束（"不得使用 eval()"）、设计指导（"优先使用函数式风格"）、历史教训混在一起，agent 分不清哪个是红线

**指令文件架构方案：**
```
AGENTS.md（50-200 行，路由器）
├── 项目概览
├── 快速开始命令
├── 全局硬约束（≤15 条）
└── 指向专题文档的链接

docs/
├── api-patterns.md      # 添加新端点时必读
├── database-rules.md    # 涉及数据库修改时必读
└── testing-standards.md # 编写测试时参考
```

**拆分后效果：** 同一任务集成功率从 45% 提升到 72%。安全约束遵循率从 60% 提升到 95%——因为规则从文件中间移到了入口文件顶部，不再被"中间迷失"。

**指令管理原则：** 每条指令标明来源（为什么加）、适用条件（什么时候需要）、过期条件（什么时候可以删）。定期审计，像管理代码依赖一样管理指令。

### L05 — 让跨会话的任务保持上下文连续

**核心困境：** 上下文窗口有限，长任务一定会跨会话，跨会话一定会丢信息。解决方案不是更大的窗口，而是更好的状态持久化。

**"上下文焦虑"深层机制：**
- Sonnet 4.5：上下文焦虑足够严重，压缩（compaction）单独不够用，上下文重置（context reset）成为 harness 设计的关键组件
- Opus 4.5：这种行为大幅减弱，可以不依赖重置而靠压缩管理上下文
- **启示：harness 设计需要对目标模型有具体的理解，不能套用通用模板**

**状态持久化三工具：**
1. `PROGRESS.md`：当前状态（commit hash、测试状态、lint 状态）、已完成、进行中、已知问题、下一步
2. `DECISIONS.md`：什么决策、为什么、什么时候做的、否决了什么方案
3. Git 提交作为检查点：每完成原子工作单元就提交，commit message 说清楚做了什么和为什么

**"上班/下班"流程：**
- 上班：读 PROGRESS.md → 读 DECISIONS.md → `make check` 确认一致 → 从"下一步"继续
- 下班：更新 PROGRESS.md → `make check` 确认一致 → 提交所有已完成工作

**定量效果：** 有状态持久化时，重建时间减少约 78%，功能完成率从 58% 提升到 100%，隐含缺陷率从 43% 降到 8%。

### L06 — 让 agent 每次工作前先初始化

**核心论点：** 初始化和实现的优化目标完全不同——初始化最大化后续实现的可靠性和效率，实现最大化已验证功能的数量和质量。混在一起只会互相拖后腿。

**混合方式的隐蔽代价：**
- 基础设施搭不牢（agent 80% 精力写功能，20% 随便搭基础设施）
- 未验证的累积（测试框架配好前写的代码，回头补测试时发现设计就有问题）
- 上下文预算浪费（配环境消耗大量预算，留给实现的不够）
- 隐式假设埋雷（第一个会话选的测试框架，第二个会话不知道，引入了另一套）

**启动就绪清单（四条件）：** 能启动、能测试、能看进度、能接手下一步。

**Anthropic 实验数据：** 使用独立初始化阶段的项目，多会话场景中功能完成率比混合方式高 31%。初始化阶段投入的时间在后续 3-4 个会话中完全收回。

**热启动策略：** 用项目模板（create-react-app、fastapi-template 等）预置标准化的基础设施，agent 只需做项目特有的初始化。

### L07 — 给 agent 划清每次任务的边界

**核心发现：** Agent 天生有"多做一点"的冲动。同时做太多事情，每一件都做不好。

**数学模型：** 上下文容量 C，同时激活 k 个任务，每个任务平均获得 C/k 推理资源。当 C/k 低于完成单个任务所需的最小阈值时，所有任务都做不完。

**Anthropic 实验数据：** 使用"小下一步"策略（WIP=1）的 agent，任务完成率比使用宽泛提示的 agent 高 37%。Agent 生成的代码行数和实际完成的功能数量呈**弱负相关**——写得越多，完成得越少。

**WIP=1 工作流：**
1. 任何时刻只允许一个任务处于"进行中"状态
2. 当前功能点端到端验证通过后，才能开始下一个
3. 不要在实现功能 A 时"顺便"重构功能 B

**"完成证据"必须是可执行的：** "代码看起来没问题"不算完成，"curl 返回 201"才算。`VCR = 已通过验证的任务数 / 已启动的任务数`，VCR < 1.0 时阻止新任务启动。

**对照实验：** WIP=1 vs 无约束。总代码量 800 行 vs 1200 行（更少），但有效代码更多。完成率 87.5% vs 37.5%。

### L08 — 用功能清单约束 agent 该做什么

**核心论点：** 功能清单不只是备忘录，它是整个 harness 的基础结构（原语）。调度器靠它选任务，验证器靠它判完成，交接器靠它生成报告。

**三元组结构：** 每个功能项必须包含 `(行为描述, 验证命令, 当前状态)`，缺一项就不完整。

**功能状态机（四状态）：**
```
not_started → active → passing
                  ↓
               blocked
```
状态转移由 harness 控制，agent 不能直接把状态改成 `passing`。通过验证命令执行成功是唯一的升级路径。

**"文档 vs 原语"的区别：** 文档可以被忽略，原语不能被绕过。类比数据库触发器约束（引擎强制执行）vs 应用层检查（可能被绕过）。功能清单作为原语承担数据库级别的约束角色。

**定量结果：** 使用结构化功能清单的项目，功能完成率比自由形式高 45%，零重复实现。

### L09 — 防止 agent 提前宣告完成

**核心科学事实：** Guo et al. (2017, ICML) — 现代神经网络系统性地过度自信。Agent 的"觉得做完了"和"实际做完了"之间存在系统性偏差。

**滑坡效应：** 代码看着还行 → 基本检查通过 → 跳过了全面验证 → "代码看起来没问题"被当作"功能已完成"。每一步都在丢失信息。

**三层终止检查：**

| 层级 | 检查内容 | 能检测 | 不能检测 |
|------|---------|--------|---------|
| 第一层 | 语法与静态分析 | 拼写错误、类型错误 | 逻辑错误、运行时行为 |
| 第二层 | 运行时行为验证 | 单元测试、集成测试、应用启动 | 跨组件交互问题 |
| 第三层 | 系统级确认 | 端到端测试、用户场景模拟 | — |

**关键约束：** 第 N 层没通过时，不许进入第 N+1 层。核心功能没验证通过之前，不许做重构（Knuth："过早优化是万恶之源"）。

**"干活的人"和"检查的人"必须分离：** Anthropic 研究发现，agent 被要求评估自己工作时，系统性地过度正面评价。同一个模型既生成又评估，内在地倾向对自己慷慨。解决方案是独立的 evaluator agent。

**面向 agent 的错误消息三要素：** 什么出了问题 + 为什么 + 怎么修（具体到文件路径和修改方法）。

### L10 — 跑通完整流程才算真正验证

**Google 测试金字塔的启示：** 大量单元测试是基础，但如果你止步于此，就会系统性地漏掉组件交互问题。

**单元测试的五类系统性盲区：**
1. 接口不匹配（渲染进程传相对路径，预加载脚本期望绝对路径）
2. 状态传播错误（ORM 缓存与数据库 schema 不一致）
3. 资源生命周期问题（文件句柄、连接池跨组件泄漏）
4. 环境依赖性（测试环境 mocks 一切 vs 真实环境配置差异）
5. 错误传播链断裂（服务层异常未被 UI 层正确捕获）

**端到端测试改变 agent 行为的机制：** 当 agent 知道它的工作要过端到端测试时，它会主动考虑组件交互、尊重架构边界、处理错误路径。

**"审查反馈提升"循环：** 每次在代码审查中发现新类型的 agent 错误 → 把它变成自动化检查 → harness 自动变强。一个月后 harness 会比月初强得多。

**架构约束的可执行化：** OpenAI 的原则是"执行不变量，不微管实现"。例如要求"数据在边界解析"但不规定用哪个库。每条架构约束都有对应的自动化检查，错误消息包含修复指导。

### L11 — 让 agent 的运行过程可观测

**双层可观测性模型：**

| 层次 | 回答的问题 | 信号类型 |
|------|-----------|---------|
| 运行时可观测性 | "系统做了什么" | 日志、追踪、进程事件、健康检查 |
| 过程可观测性 | "为什么这个变更应该被接受" | 计划、评分标准、验收条件、冲刺合同 |

**无 vs 有可观测性对比（"暗色模式"任务）：**
- 无：循环 3-4 次，总耗时约 45 分钟，勉强产出
- 有：一次迭代出高质量结果，总耗时约 15 分钟
- **效率差 3 倍，区别只在可观测性**

**"冲刺合同"（Sprint Contract）：** 编码开始前，生成者和评估者协商一份合同，明确任务范围、验证标准、排除项。防止"生成者做了评估者因可预见原因立即拒绝的东西"。

**评估评分标准（Evaluator Rubric）：** 把"好不好"变成四维可量化评分（代码正确性、架构合规、测试覆盖、视觉设计/代码质量），每维有硬性阈值，任一不达标则 sprint 失败。

**Anthropic 三 agent 架构实验数据（DAW 任务，Opus 4.5）：**
- Planner：4.7 分钟，$0.46
- Build R1：2 小时 7 分钟，$71.08
- QA R1：8.8 分钟，$3.24
- Build R2：1 小时 2 分钟，$36.89
- QA R2：6.8 分钟，$3.09
- Build R3：10.9 分钟，$5.88
- QA R3：9.6 分钟，$4.06
- **总计：3 小时 50 分钟，$124.70，产出可正常游玩的应用**

### L12 — 每次会话结束前都做好交接

**核心原则：** 熵增是默认方向。Lehman 软件演化定律——一个持续变更的系统，如果没有人主动管理，复杂性一定会增加。

**清洁状态五条件（完成的真正定义）：**
1. 构建通过
2. 测试通过
3. 进度已记录（功能清单已更新）
4. 临时工件已清理（调试日志、注释掉的代码、TODO）
5. 启动路径可用（新会话能不靠人工干预直接开始工作）

**12 周对照实验（有清洁策略 vs 无）：**

| 指标 | 无清洁策略（第12周） | 有清洁策略（第12周） | 差距 |
|------|-------------------|-------------------|------|
| 构建通过率 | 68% | 97% | +29pp |
| 测试通过率 | 61% | 95% | +34pp |
| 新会话启动时间 | 60+ 分钟 | 9 分钟 | -85% |
| 过时工件 | 103 个 | 11 个 | -89% |

**双模式清理策略：**
- 即时清理（每会话结束）：清理临时文件、更新功能清单、确保构建和测试通过
- 定期清理（每周一次）：全面系统扫描、处理累积结构性问题、更新质量文档

**Harness 简化原则：** 随着模型能力提升，主动移除不再必要的组件。Anthropic 实验：Opus 4.6 发布后，任务拆分机制反而成了多余的步骤。移除后 Builder Agent 能连续工作超两小时而不偏离方向。**推荐做法：** 每月禁用一个组件跑基准任务，无退化则永久移除。

## 五、关键概念速查表

| 概念 | 定义 | 出处 |
|------|------|------|
| **能力鸿沟** | 模型在基准测试 vs 真实任务上的表现落差 | L01 |
| **Harness 诱导失败** | 模型能力足够但因执行环境结构性缺陷而失败 | L01 |
| **验证缺口** | agent 自评完成与实际正确性之间的偏差 | L01 |
| **上下文焦虑** | 上下文快满时 agent 匆忙收尾、跳过验证的行为 | L01, L05 |
| **知识可见性缺口** | 项目总知识中不在仓库里的比例 | L03 |
| **全新会话测试** | 全新会话只看仓库回答五个关键问题的测试 | L03 |
| **发现成本** | agent 找到一条关键信息需要消耗的上下文预算 | L03 |
| **指令信噪比（SNR）** | 文件中与当前任务相关的指令占总指令的比例 | L04 |
| **中间迷失** | LLM 对长文本中间部分的信息利用效率显著低于两端 | L04 |
| **重建成本** | 新会话恢复到可执行状态所需的时间 | L05 |
| **漂移（Drift）** | agent 理解与代码仓库实际状态之间的偏差 | L05 |
| **启动就绪清单** | 项目能被全新 agent 无歧义操作的四条件 | L06 |
| **过度延伸（Overreach）** | agent 一次激活超出最优数量的任务 | L07 |
| **不足完成（Under-finish）** | 已启动任务中通过端到端验证的比例低于阈值 | L07 |
| **WIP=1** | 限制同时只进行一个任务，来自 Kanban 方法论 | L07 |
| **完成证据** | 从"进行中"变为"已完成"必须满足的可验证条件 | L07, L08 |
| **功能状态机** | not_started/active/blocked/passing 四态，harness 控制转移 | L08 |
| **三元组结构** | 每个功能项：(行为描述, 验证命令, 当前状态) | L08 |
| **三层终止检查** | 语法分析 → 运行时验证 → 系统级确认 | L09 |
| **置信度校准偏差** | agent 自报完成信心与实际完成质量之间的系统性差距 | L09 |
| **冲刺合同** | 编码前协商的范围/验证标准/排除项协议 | L11 |
| **双层可观测性** | 运行时可观测性 + 过程可观测性 | L11 |
| **审查反馈提升** | 重复代码审查意见 → 自动化检查的转化流程 | L10 |
| **清洁状态五条件** | 构建通过、测试通过、进度记录、工件清理、启动可用 | L12 |
| **Harness 简化** | 随模型能力提升主动移除不再必要的组件 | L12 |

## 六、与 Superpowers 的对比

| 维度 | Learn Harness Engineering | Superpowers |
|------|--------------------------|-------------|
| **定位** | 教育课程，系统化知识体系 | 生产级技能插件，运行时强制执行 |
| **方法论** | 五子系统 + 五层防御的理论框架 | TDD 应用于行为工程 + 理性化防御系统 |
| **执行方式** | 理论讲授 + 实战项目 | 会话启动引导注入 + 技能自动触发 |
| **核心工具** | AGENTS.md、feature_list.json、PROGRESS.md | Skill 工具调用 + 子Agent派发 + 两阶段审查 |
| **Agent 心理模型** | 上下文焦虑、过度自信、捷径行为 | 理性化表格、红牌列表、铁律声明 |

## 七、总结

Learn Harness Engineering 是一座连接 AI 能力与软件工程可靠性的桥梁。它的核心贡献在于：

1. **精确的概念体系：** 将"agent 不好用"这个模糊的抱怨分解为可诊断、可修复的具体问题。每次失败都能归因到五层防御中的某一层。

2. **可操作的方法论：** 不是"多写点文档"的空泛建议，而是"新建会话能只看仓库回答五个问题吗？"的具体测试。

3. **基于实证的工程设计：** 每个结论都来自 OpenAI 和 Anthropic 的实际实验数据——SWE-bench 的通过率、对照实验的完成率、12 周长期演化的构建通过率。

4. **系统化的质量框架：** 从指令的 SNR 到 WIP=1 的约束，从三层终止检查到清洁状态五条件，每个环节都有明确的判定标准。

5. **渐进式的实战路径：** 六个项目从"对比提示词和规则"到"搭建完整可观测工作环境"，构成了完整的学习和部署曲线。
